# Angat — a local-first AI companion that helps you rise, one small goal at a time

Angat is our hackathon entry for building software that remains useful when the cloud is unavailable.

It is a private, offline-first self-improvement app for Android. The user completes a short onboarding assessment, receives three small daily goals generated by a local language model, earns XP by completing them, and can ask Bambot to read and act on app data through controlled tools.

The important part is the boundary: the model can reason and request a tool, but the app owns validation, permissions, persistence, XP, safety rules, and confirmation. No cloud model is silently used.

## The demo in one sentence

Sign in once, complete onboarding, install a small local Qwen model, generate three achievable goals on-device, complete one, earn XP, then ask Bambot about your real quests, progress, notes, and next step — with the network disabled.

## Why this fits the hackathon

Angat is designed around graceful degradation:

- AI inference runs locally on the phone.
- Daily goals are generated by the installed local model, not a remote API.
- User state is stored locally first.
- XP, levels, ranks, quest rules, and safety validation remain app-owned.
- The app waits honestly when no local model is installed instead of showing fake goals.
- Account backup is optional infrastructure for identity, onboarding answers, notes, and XP; it is not the AI runtime.
- Tool calls are typed, allowlisted, confirmed when needed, and verified by reading the result back.

## What is implemented

### Onboarding and player profile

- Google sign-in through Supabase Auth.
- A four-page assessment covering routine, goals, blockers, life-area ratings, and boundaries.
- Deterministic local analysis of onboarding answers into eight life-area stats.
- Ordered Insight 1 and Insight 2 with evidence/provenance.
- Profile data survives restart through local repositories.

### Local AI and Bambot

- Native React Native inference through `llama.rn` / llama.cpp.
- Qwen3 1.7B Q4 is the current default model.
- Qwen3.5 0.8B Q4 is available as an experimental, much smaller option.
- Retired Gemma entries remain visible only for compatibility with old installs.
- Model files are downloaded and checksum-verified on the device.
- Bambot can read typed app tools for profile, stats, insights, onboarding context, quests, XP/rank, check-ins, notes, memory, and model status.
- `notes.create` is the first enabled write tool. It requires confirmation, local persistence, idempotency, and read-back verification.
- No arbitrary filesystem, code, shell, SQL, network, cloud, or direct XP tools are exposed to the model.
- Chat output removes raw reasoning/tool envelopes and separates a short “What I checked” summary from the final answer.

### Daily goals

- When a model is not installed, the daily quest board stays empty and shows a loading/install state.
- When a model is ready, Bambot generates exactly three small daily goals locally.
- The app rejects malformed, unsafe, too-long, high-energy, or impractical model output.
- Generated goals are persisted locally and become normal validated quests.
- Completion requires an app-private proof photo, applies the XP cap, and records durable progress.

### Progress

- XP is persisted locally and backed up using max-XP merge semantics.
- Level and rank are derived from persisted XP.
- Bambot’s visual stage is derived from level.
- Streaks and rest tokens are not finished yet and currently display zero.

## Architecture

```text
React Native UI
    |
Zustand presentation store
    |
Bambot agent service
    |
Typed tool registry and confirmation layer
    |
Domain services and validators
    |-----------------------------|
SQLite/local files              llama.rn
    |                             |
real app state              local Qwen model
```

The model never writes directly to SQLite or files. A tool request must pass schema validation, app policy, revision/idempotency checks, user confirmation when required, domain execution, and read-back verification.

## Quick start: UI-only Expo Go demo

This mode is useful for reviewing the navigation and screens. Expo Go is not enough for local LLM inference, voice recognition, or the full native Android app.

Requirements:

- Node.js 22 recommended.
- npm 10+.
- Expo CLI through the project’s local `npx` command.

```bash
cd apps/buddy
npm install
npm start
```

Scan the QR code with Expo Go.

For Google OAuth in Expo Go, use the tunnel command because Supabase may reject a LAN IP redirect:

```bash
npm run start:tunnel
```

## Configure Google and Supabase

The app can compile without Supabase variables, but the full onboarding demo requires Google sign-in.

1. Copy the example environment file:

```bash
cd apps/buddy
cp .env.example .env.local
```

2. Add only:

```text
EXPO_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLISHABLE_KEY
```

Never put a service-role key, database password, OAuth client secret, or private key in the app environment.

3. In Supabase:

- enable Google under Authentication → Providers;
- configure the Google web OAuth callback:
  `https://YOUR_PROJECT.supabase.co/auth/v1/callback`;
- add redirect URLs for Expo Go and the native scheme:
  `exp://**`
  `buddylevelup://**`.

4. Apply the migrations in `apps/buddy/supabase/migrations/`.

The cloud stores identity, onboarding backup, notes backup, and XP backup according to the current ADRs. The device remains the source of truth for unsynchronized local work and the local model never depends on cloud inference.

## Build the native Android app

Expo Go cannot load the native inference module. Use a development build.

Before building, connect an Android device with USB debugging enabled:

```bash
adb devices -l
```

Then:

```bash
cd apps/buddy
npm run android
```

The build targets `arm64-v8a`, which covers modern Android phones such as the Pixel 9A. The first native build compiles llama.cpp and may take a long time.

To build without installing on a device:

```bash
cd apps/buddy
export ANDROID_HOME="$HOME/Android/Sdk"
export JAVA_HOME="$HOME/.local/jdk-17"
export PATH="$JAVA_HOME/bin:$ANDROID_HOME/platform-tools:$PATH"
./android/gradlew -p android app:assembleDebug \
  -x lint -x test --configure-on-demand --build-cache \
  -PreactNativeArchitectures=arm64-v8a
```

APK output:

```text
apps/buddy/android/app/build/outputs/apk/debug/app-debug.apk
```

The debug APK is for development and may expect a Metro/dev-client workflow. For sharing with other devices, use a properly signed release build. The current Gradle template uses the debug keystore for release unless a production keystore is configured; do not treat that as store-ready signing.

## Install a local model

Open the Bambot chat tab and choose a model. Tap Install model and wait for checksum verification.

Current options:

| Model | Approximate main file | Use |
|---|---:|---|
| Qwen3 1.7B Q4_K_M | 1.11 GB | Default and safer tool-calling choice |
| Qwen3.5 0.8B Q4_K_M | 533 MB plus optional projector | Experimental smaller/newer model |
| Gemma 4 E2B/E4B | Retired | Kept only for compatibility with existing installs |

Qwen3.5 is experimental. It must still be tested on the Pixel 9A for generation speed, tool-call reliability, image support, and memory use before becoming the default.

The model files are not committed to Git. The app verifies the pinned file size and SHA-256 before loading them.

## Offline acceptance walkthrough

1. Start the app while online.
2. Sign in with Google and complete onboarding.
3. Install Qwen3 1.7B or Qwen3.5 0.8B from the Bambot model controls.
4. Wait until the model status says ready.
5. Open Today and confirm three locally generated goals appear.
6. Enable airplane mode and disable Wi-Fi.
7. Force-close and reopen the app.
8. Ask Bambot to read your stats, quests, XP, notes, and insights.
9. Ask Bambot to create a todo.
10. Confirm the write.
11. Verify the todo appears locally and survives restart.
12. Complete a quest with the required proof photo.
13. Confirm XP, level, and rank update.
14. Verify no cloud request, model fallback, or silent remote inference occurs.

## Honest current limitations

- Streaks and rest tokens are not implemented; they currently remain zero.
- Chat history is session-local and is not restored after restart.
- Qwen3.5 0.8B is experimental and not yet proven better for structured tool calls.
- Audio attachments are not sent to the model.
- iOS native inference is not verified.
- The model is downloaded separately and is not bundled in the APK.
- A release build needs a real signing key before distribution.
